# ADR-007 — Immutable closure and explicit local publication candidates

Status: **Experimenting / review proposal**, E0.M4; full assembly-wide Latest/Pinned product behavior remains E4.M4. CAD-R006–008.

An immutable version is a content hash, not a working revision or recovery checkpoint. Publication references a retained immutable version plus a channel and monotonic sequence. One source's writer lease serializes local publication ordering. A uniquely greatest published sequence in the requested channel is Latest; conflicting greatest versions return ambiguity. There is no global/channel-branch ordering across unrelated documents, no background mutation of historical releases and no cloud publication.

External dependencies retain source document+definition identity, policy, requested/effective version, relative locator and complete verified effective snapshot. Paths are hints inside the current authorized Platform root, never identities. Pinned always requests its original version. Missing/moved/replaced/incompatible source preserves its embedded closure and reports a visible state. Relocation is an explicit locator edit followed by identity verification; there is no arbitrary search or nearest-geometry retargeting.

Refresh is read-only with respect to the saved/working document. Compatible Latest produces an ephemeral revision-bound candidate. A worker must validate that exact candidate's graph, pinned runtime, actual geometry, references and effective closure; adoption rechecks both consumer revision and source bytes. Failure/cancellation/staleness never partially applies. Saving source publication and consumer adoption are separate recoverable stages. Full multi-source atomic publication and automatic working-assembly following are not claimed.

Compatibility is deliberately narrow: stable definition/feature IDs and types, declared datum roles, selector/profile identity and supported operation family must agree; historical/current producer references must be proven. Changed dimensions in the tested extrusion family may proceed. Unsupported runtime, missing roles, operation-family changes or a current spatial probe requiring unproven external mate propagation remain pending. E4.M4 must integrate full feature/mate/interference/drawing compatibility; this E0 gate does not silently certify arbitrary surface mates.

Local drawing views reference an explicit retained model version and independent drawing revision. Editing a note advances drawing revision; working-model changes do not silently rebind it. Snapshot closure includes required local model versions and external effective content. These are tested storage bindings, not rendered drawing/BOM acceptance. Referenced versions cannot be deleted; historical closure stays immutable when a new effective source is adopted.

Fixture evidence: two instances share one cached source definition with different transforms; source extrusion width40→60 changes volume12000→18000 mm³ after explicit validation/adoption; prior consumer version still contains the old source snapshot. Pinned stays fixed; ambiguous/incompatible/missing/foreign sources preserve cache; internal/external cycles fail; copied/offline documents regenerate under the pinned runtime. See [tests](../../tests/native.test.mjs) and [browser flow](../../tests/browser-native.mjs).

Consequences: bounded embedded snapshots simplify portable/offline correctness at the cost of document growth and limited closure depth. Larger stores may move to a validated Merkle/blob container through migration. Preserve v1 contents and original sources; never weaken identity or scope to make a fixture pass. Owner acceptance is pending, separately from experimental publication.
