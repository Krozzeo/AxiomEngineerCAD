# Instructions for coding agents

1. **Read [MASTER_DESIGN.md](MASTER_DESIGN.md) v0.2 in full before planning or editing.** It is the canonical approved product-intent and roadmap source; nothing in it proves a feature has been implemented. Read the specialized architecture/quality/security contracts linked in §2.4 for the current milestone.
2. Inspect current code, branches, PRs and accepted Platform contracts before acting. Do not assume that historical SHAs or experimental provider PRs are current or integrated.
3. Begin at the next unaccepted Engineer Milestone, initially **E0.M1**. Each milestone needs its **type-specific** real proof (executable spike/ADR, domain command/fixture, or actual human UI), negative/recovery tests and exact evidence. Do not fabricate UI or model capability to satisfy a blanket checklist.
4. Platform owns generic Hub/local lifecycle, account/provider credentials and shared AI/review SDK. Engineer owns all exact B-Rep, solvers, parametric history, versions, assemblies, drawings and semantic CAD tools. Game Engine is a reference for proven patterns, not a source of shared CAD domain types.
5. Never bypass human-reviewed AI Apply, document revisions, stable IDs, unit/geometry validation, authorization or atomic persistence. Never claim GPU, live-model, migration or numerical acceptance based on a mock or visual approximation.
6. Propose an ADR and ask for owner approval when a technical spike reveals that a foundational decision or MVP scope must change. Preserve old documents, tested revisions, branches and user files.
7. Freeze native schema only after E0.M2 topological and E0.M3 spatial-solver evidence, then validate E0.M4 document/reference/version graph, E0.M5 tool transaction and E0.M6 drawing/GPU/security. Do not proceed beyond E0.M7 without owner-reviewed Go/Redesign/Stop evidence.
8. Treat per-task provider exposure as an explicit engineering IP permission; local-only tasks never silently upload geometry/drawings. Distinguish a reviewable geometrically correct drawing from an unapproved manufacturing release.
9. Once implementation starts, maintain current `IMPLEMENTATION_STATUS.md`, `AI_HANDOFF.md`, milestone reports and relevant ADRs; distinguish planned work from completed and externally validated work.
10. **Owner delivery requirement:** whenever a new Engineer Milestone is completed for review, prepare and publish its compatible experimental installation so the owner can download, install and run it from Axiom Platform. A source branch/PR alone is not delivery. Require passing exact-commit CI, preserve immutable previous builds, publish the ZIP plus `axiom-release.json` with verified size/hash and PR/build provenance, and verify actual Platform discovery/install/launch. This instruction authorizes milestone experimental publication; it does not imply merge to main, stable release or milestone acceptance. Report the installable version/link and any actual delivery blocker.

For architecture and third-party sources, follow the links in the master's **Axiom family and source references** section.
